## 1. 実施方法と正本

Canon TDDの一次資料は「シナリオ一覧を作り、そのうち1件を実行可能テストにして、既存テストとともに通し、必要なら整理して反復する」とする。最初から全行をテストコード化しない。本書の作業順やPR運用は、その方法に合わせた本プロジェクト向けの提案である。[S17]

```text
合意した要件＋Test List
  → 次の1シナリオを具体化
  → REDを確認
  → 対象＋既存回帰をGREEN
  → 必要な整理
  → 一覧に発見を追加して次へ
```

`requirements/`は合格基準、`tests/`は検証実装、CIは実行者、`reports/`は版付き証拠。別の完了判断エンジンや新packageは作らない。現行の実行入口を整理するときも、通常のnpm testとは別のbrowser proofを取りこぼさない。[S01][S05]

**REDフェーズの完了と、製品機能の完成は別。** 正しい負例を拒否できるテストはGREENである。REDとは、その振る舞いを要求するテストが失敗することを指す。起動不能・通信故障・#206の無関係な既知失敗を、機能不足のREDの代わりにしない。[S03]

既存の成立済み振る舞いは回帰として継承する。新しい経路で未達ならその差分のREDを示すが、RED作成のために既存実装を意図的に退行させない。構造制約はユーザーが合意した4 packagesと決定権の境界だけを対象とし、内部関数名やtree上の全ファイル名までテストで固定しない。[S01]

### 1.1 各シナリオが実行可能になる前に必要な情報

| 項目 | 必須内容 |
|---|---|
| 根拠 | 要件ID、根拠の版と箇所、維持／追加／明示変更の別 |
| 前提 | 確定入力、根拠参照、固定資源、実行環境、権限と保存モード |
| 操作 | 公開入口への入力または実ユーザーgesture。private helperの直叩きだけで往復成功にしない |
| 期待結果 | 独立して定めた値・関係・可視内容・許可操作・追記先／追記回数・失敗状態 |
| 証明範囲 | coreだけ、adapter契約、実ブラウザ、実接続、外部reviewを区別 |
| RED理由 | 何のassertionが、どの機能不足で失敗すべきか |
| GREEN証拠 | 実装commit、入力hash、依存・条件・環境、検証結果、必要な受理記録 |

同じテストが複数の要件を証明してよい。逆に一つの要件が複数レベルの検査を必要とすることもある。行数・ファイル数・code coverage率を完了条件にしない。期待値は実装結果の自動転記で作らず、数値・意味を独立して定める。[S17]

### 1.2 状態ラベル

本書の各行はすべて`LISTED／NOT_RUN`であり、REDまたはGREENの実測結果ではない。「保持」は現行資料にある意味を維持する対象、「追加」は#207または#205の完成に必要な候補、「確認」は合意・詳細調査が先に必要な項目、「構造」「検査」は合意境界や完了判定そのものの検証を示す。

`保持`でも新経路で成功済みとはしない。現行資料のどこまでを読んだかは出典表と未決事項に残す。

## 2. PR／worktreeの進め方

| フェーズ | 先に閉じること | 主なシナリオ領域 |
|---|---|---|
| P0：全体契約と基準 | 基準を固定し、全要件・既存検査の対応、公開入力と限界をレビューする。#206は別作業として切り分ける | BL、EV、Q01–Q08 |
| P1：最小core | 1つの確定UI要素をreduceし、固定条件から表示入力を作る。参照検証と失敗状態の最小形 | IN、RC、TRの基本 |
| P2：通常UIの縦経路 | 最小入力から実公式A2UIを経てText／binding／操作通知へ到達する | UI、RTの最小起動 |
| P3：図の縦経路 | A2UI図部品へruntimeがmaxGraphを注入し、確定Sceneをそのまま描画する | GR、UI-06、RSの基本 |
| P4：ローカル往復 | 表示変更を候補・受理・UIイベントへ戻し、fresh browserで復元する | ED、ACのローカル、RP |
| P5：上流と外部の往復 | 追跡／整合、変更先分類、上流更新後の再設計、外部確定不明を区別する | TR、UP、ACの外部 |
| P6：表現意味の全展開 | 既存図種・集合・時間・chart・地図・製品別意味を新経路へ移す。#205の拡張は別の受入範囲のまま紐付ける | ST、SQ、CH、GE、EX、GR |
| P7：周辺機能の移管 | URL・資源・module・出力・配布・旧shell責務を残らず移す | RT、RS、EX、AR |
| P8：退役・統合DoD | 新経路の実証後に旧経路を消し、最終cutで必要な全検証と証拠を揃える | AR、EV、全必須シナリオ |

この表は領域別の順序であり、各フェーズを巨大な一括REDにする指定ではない。各フェーズ内で`RED_i → GREEN_i → 必要な整理`を繰り返す。

```text
契約PR/worktree
  → RED-1 PR/worktree
  → GREEN-1 PR/worktree
  → RED-2 PR/worktree
  → GREEN-2 PR/worktree
  → … → 統合PR/worktree
```

後続は前段から派生し、前段merge後にrebaseする。その時点で対象テスト・回帰を再実行し、証拠を新しいcommitへ結び直す。差分がなくても古いcutの証拠を現在の証拠とは呼ばない。独立した整理だけを別PRにしてもよいが、同じ対象に未GREENの変更を積み続けない。

REDだけのPRをmergeするかどうかは、機能完成判定と別のmerge判断である。既知の#201例外許可を流用しない。RED証明が揃った場合でも「製品の必須テストが失敗中」という事実を保持し、`skip`や全面的な失敗無視でGreenに塗り替えない。[S03]

## 3. 最初の具体的なREDと縦経路

最初の候補は **RC-01：固定根拠とliteral Text一つを持つ確定UIイベントから、正しいUI状態が得られること**。Q01で最小公開契約を決めてから実行可能化する。

| 項目 | 具体化案 |
|---|---|
| 前提 | テスト用に受理された意思決定`d-01@1`の`/title`が`案件A`。表示設計でliteral値`案件A`を確定したText `t-01`と、その根拠参照を持つUI定義。reduceに上流業務状態の生成や外部取得を要求しない。これは架空fixtureであり実業務の受理ではない |
| 操作 | 公開されたcore入口から、確定UI定義イベントをreduceする |
| 期待 | UI状態の対象`t-01`の表示値が正確に`案件A`で、根拠対応が保たれ、入力の決定内容は変わらない |
| REDの意味 | 処理は実行されたが対象が欠落・誤値・誤参照になる。module未発見だけの失敗を意味検証の証拠にしない |
| このテストでまだ証明しないこと | A2UI実描画・maxGraph・gesture・外部承認・業務上の適切さ |
| GREEN後の次候補 | 誤った根拠版の拒否 → compile → 実A2UI Text表示 → 実図部品 → ローカル保存操作 → fresh再構築 |

続いて **TR-07** では、根拠が「警告を表示すること」を明示しているのに、正しい参照を付けたUIが警告を省く負例を作る。参照が有効なだけで受理する実装なら、その検査はREDになる。これは任意の自然言語を完全判定する要求ではなく、具体化した条件の反例である。

**ED-04** では、上流変更の操作直後に上流候補だけが送られ、UI定義logは未変更であることを確認する。その後、上流受理・UI整合評価・必要な再設計とUI受理を経た段階では、UI定義への別の確定が発生し得る。「上流操作はUI logへ永久に何も書かない」という誤った解釈にしない。

**RP-01** では、最初の表示が独立した期待値を満たすことを確認した上で、全表示状態を捨てる。再生前後が同じという比較だけでは、同じ誤表示が2回できただけかもしれないため、それ単独を意味充足の証明にしない。

## 10. 最終DoD

```text
DONE
  = 合意した維持要件＋追加要件がすべて識別されている
  AND 全必須シナリオに有効な検証と必要reviewが対応する
  AND 同じ実装・入力・依存・描画条件・環境に対応する証拠が揃う
  AND 正規の実描画・変更先別の実操作往復・fresh再構築が成立する
  AND 必須範囲に未実行・UNKNOWN・失敗・証拠欠損が残らない
  AND 新経路の意味充足後に旧経路の退役を確認している
```

条件付きCIが既存にあることと、最終DoDで必須証拠を欠いたまま成功とすることは別である。どの条件で何を実行するかも基準化する。重い検証を無条件に全PRで増やすこと自体を目的にしない。[S04]

機械検証が必要な外部review記録を確認しても、業務判断の真理や任意入力すべての無欠損を数学的に証明したことにはならない。宣言した要件・対応範囲・反例・対象版の中で主張を閉じる。未定義の全機能まで含めて「欠損0」と称しない。

**今回完了したのはTest Listの初版作成と文書の対応検査であり、上記DONEではない。** 次の実装単位はRC-01を最初の候補とし、Q01と基準レビューの成立後に1件ずつ実行可能化する。
